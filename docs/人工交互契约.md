# 人工交互契约（v1）

> 状态：v1 设计（m01410，m01681 修正）。团队 agent 是普通 DSH 会话，Host 不拦截输入；Web UI 默认用 composer block 禁用绑定 worker 的输入框。本文定义“推荐路径”和“直接路径”的边界：建议与提问走主 Agent；直接输入仍可由 API、脚本或其他客户端发生，引擎只观察留痕。
>
> 相关文档：[总体设计](./总体设计.md) · [团队配置文件字段规范](./团队配置文件字段规范.md) · [节点激活消息契约](./节点激活消息契约.md) · [智能体初始化消息契约](./智能体初始化消息契约.md)

## 1. 目的

团队引擎把每个 agent 拉起成一个真实 DSH 会话。真实会话天然带输入框，团队插件不拥有它，也不应该假装拥有它。但“随便说”与“团队级交接”是两件事：

- **直接说话**是 DSH 会话的原生能力，适合澄清、追问、给上下文；
- **建议/提问**是团队协议对象，带来源、状态、审计与 activation 绑定，适合跨节点、需要留痕的变更。

因此 v1 采用“推荐主 Agent；Host 不拦截；Web UI 默认禁用 worker composer”：

- **主 Agent**（front-desk）是推荐的团队前台，负责解释状态、转达建议、代办提问。
- **worker** 是团队引擎调度的执行会话；Host 仍可接受输入，但 Web UI 默认把它的 composer 置为 inert。
- 用户对 worker 的团队级意见推荐以 **Suggestion（建议）** 形式经主 Agent 转达。
- worker 需要用户决策时以 **Question（提问）** 形式交给主 Agent 代办，用户回答后由主 Agent 交回。

直接对 worker 说的话不会被 Host 拒绝；Web UI 默认不允许这样输入，但 API、脚本或其他客户端仍可写入。这类输入不会自动变成 Suggestion/artifact，只作为该会话的普通输入存在。需要团队级留痕、跨节点生效或进入 run 记录时，走主 Agent。

“主 Agent”不是引擎，也不是某个隐藏的调度器。它是引擎初始化时自动生成的保留 agent，`team_role=master`，默认 id `team-master`；用户不在 `team.json` 中手写它。引擎把它写入运行时有效配置与 `state/master.json`，并像普通 agent 一样用标准 `session.create` 为它创建会话。

## 2. 不变量

1. 有效配置恰好一个主 Agent；它由引擎生成（`team_role=master`），不在用户 `agents` 中，不得被任何 pipeline node 引用，不得定义 `receivers`。用户配置的 agent 只能写 `team_role=slave` 或省略；手写 `master` 被拒绝。
2. Host 不拦截 `session.prompt` / steer，不创建“只读会话”类型；用户对任一团队会话的输入都是合法 DSH 输入。
3. 主 Agent 是推荐前台，不是唯一入口；它与 worker 在 Host 输入能力上没有类型差异。Web UI 默认通过 composer block 隐藏 worker 的直接输入，这是展示策略，不是 Host 鉴权。
4. 用户建议只能由主 Agent 通过 `team_send_suggestion` 进入团队；worker 不得把自己的输出伪装成用户建议。用户直接对 worker 说的话不是 Suggestion。
5. 建议是**建议**，不是越权指令。worker 可以基于角色、验收标准或安全约束拒绝，但必须给出理由并回应建议。
6. 提问必须绑定到一次 activation；activation 结束后到达的回答不再生效。
7. 一个 worker 同时最多 `maxPendingQuestionsPerAgent` 个 pending 提问（默认 1）。
8. 所有建议与提问都有来源、时间、状态；状态变化写入事件日志，可审计。直接输入另记 `human.direct-input`（摘要，不记正文）。
9. `workerComposer=blocked` 时，Client 调 `ctx.conversation.blocks.set(sessionId, { reason })`；该 block 只影响 Web UI，不覆盖其他插件已有的 block，清理时只在 reason 等于自己的文案时 clear。

## 3. 会话绑定与输入展示

### 3.1 绑定类型

`state/bindings.json` 中每个 agent 一条绑定，新增字段：

| 字段 | 值 | 说明 |
|---|---|---|
| `teamRole` | `master` \| `slave` | 由有效配置的 `team_role` 派生。 |
| `generated` | boolean | true 表示该 agent 不在用户 `team.json` 中，是引擎补齐的 master。 |
| `kind` | `front-desk` \| `worker` | 由 `teamRole` 派生，不单独配置。 |
| `managed` | boolean | 是否由团队引擎管理；只影响 provision/调度，不影响输入。 |
| `placementState` | `unplaced` \| `provisioning` \| `standby` \| `running` \| `waiting_human` \| `failed` \| `session-lost` | 当前放置状态。 |
| `current` | object \| null | 当前或最近一次 placement：pipelineId / nodeId / runId / activationId / receiverId / iteration。 |
| `lastPlacement` | object \| null | 上一次 placement，用于 standby 时面板仍能显示“上次在哪个流水线”。 |

完整示例见 [总体设计 8.7](./总体设计.md#87-绑定账本)。

### 3.2 会话绑定当前 pipeline

用户要求“会话需要绑定当前属于哪一个流水线”。绑定账本用 `current` 表达：

```json
{
  "teamRole": "slave",
  "generated": false,
  "kind": "worker",
  "managed": true,
  "placementState": "running",
  "current": {
    "pipelineId": "delivery",
    "nodeId": "builder",
    "runId": "run_01J...",
    "activationId": "act_01J...",
    "receiverId": "rework-inbox",
    "iteration": 2,
    "startedAt": "2026-02-01T10:00:00.000Z"
  },
  "lastPlacement": {
    "pipelineId": "delivery",
    "nodeId": "builder",
    "runId": "run_01H...",
    "endedAt": "2026-01-31T18:00:00.000Z"
  }
}
```

- 一个 agent 同一时刻只执行一个 activation；`current` 指向它。
- 同一 agent 被多个 pipeline 的 node 复用时，`current.pipelineId` 是正在执行的那一个；排队中的 activation 不写 `current`。
- activation 结束后，`current` 移到 `lastPlacement`，`placementState` 回到 `standby`；面板显示“上次：需求交付 / 实现”。
- 会话从未参与运行：`placementState = unplaced`，`current = null`。
- 面板永远按 `sessionId` 查绑定，不从会话日志猜。

### 3.3 不拦截，只观察

Host 不在会话输入链路上做团队鉴权。Web UI 默认已把绑定 worker 的 composer block；本节针对 API、脚本、其他客户端或 `workerComposer=open` 的部署。引擎只订阅 `session/event`，在绑定会话出现 user-role 消息时做三件事：

1. 追加 `human.direct-input` 事件：`sessionId`、`messageId`、`agentId`、`current.activationId`、时间、摘要（正文不复制，留在会话日志）。
2. 如果该 activation 有 `pending` 的 Question，把这条消息视为回答：状态置 `answered`，`answer.source="direct"`，`answeredBySessionId` 为该 worker 会话，并通知主 Agent（避免主 Agent 重复问用户）。
3. 否则只知会主 Agent：“用户刚在 <agent> 会话直接说了话”；不改变 activation 状态，不把内容写成 artifact/suggestion，也不替 worker 做决定。

明确不覆盖：

- 不拒绝、不改写、不延迟用户消息；
- 不把直接输入注入其他 agent；
- 不因为它绕过 channel 验收就判 run 失败；
- 只读操作本来就不受影响。

代价：直接输入没有 channel 的 provenance，run 重放时只能重放引擎侧消息，不能重放用户原话。需要审计时走主 Agent 的建议/提问。

### 3.4 前端表现：worker composer block

`settings.humanInteraction.workerComposer` 默认 `blocked`。Client 在绑定解析后按以下规则处理：

- **worker，blocked**：调用 `ctx.conversation.blocks.set(sessionId, { reason: t("team.workerComposerBlocked") })`。composer 变 inert；placeholder/悬浮条提示“请到主 Agent 会话提建议或回答”，提供“打开主 Agent”按钮。
- **worker，open**：不设置 block；悬浮条显示“可直接对话；团队级建议建议经主 Agent 转达”。
- **主 Agent**：不设置 block；悬浮条显示“团队前台”和待处理提问数。
- **未绑定 / 已释放 / `managed=false`**：清除自己的 block；composer 正常。
- **worker 等待回答**：仍 blocked；提示“请在主 Agent 会话回答”，不提示在本会话回复。
- 只阻塞输入，不阻塞阅读、复制、停止正在运行的回合；不删除草稿。
- 不覆盖其他插件已有 block；清理前检查 `storeFor(sessionId).getSnapshot()?.reason` 是否等于自己的文案。
- 不弹“拒绝”toast，不删用户消息；block 是 affordance，API/其他客户端仍可输入，引擎照常记录 `human.direct-input`。

### 3.5 解除绑定

- `team down` 默认只停调度，保留绑定；worker 仍是普通会话，但 Web UI 仍按绑定 block composer（用户可读，不能输入）。
- `team down --release` 或显式 `team unbind <agentId>` 把 `managed` 置 false，记录 `binding.released` 事件；Client 清除自己的 block，会话本身不删除。
- 解除后 composer 恢复普通；再次 `team up` 重新建立绑定并重新 block。

## 4. 建议（Suggestion）

### 4.1 语义

建议表达“用户希望 worker 考虑的一件事”，来源必须是用户，经主 Agent 转达。它不是 channel，不产生 artifact，不改变图结构；它的作用是给正在执行或即将执行的 activation 增加人类上下文。

典型内容：

- 约束补充：“不要改数据库 schema。”
- 方向纠偏：“优先修登录，不要先做样式。”
- 验收补充：“报告里必须列出回滚步骤。”
- 对上一次交付的反馈：“第二轮请解释为什么跳过测试。”

建议不保证被采纳。worker 必须在回复或 `team_ack_suggestion` 中说明：接受、部分接受、拒绝及理由。

### 4.2 生命周期

```text
created → queued → delivered → acknowledged
                    ↘ expired
                    ↘ cancelled
```

| 状态 | 含义 |
|---|---|
| `queued` | 已入库，等待下一次 activation 或可 steer 的时机。 |
| `delivered` | 已注入 activation 消息或作为 steer 送达。 |
| `acknowledged` | worker 调用了 `team_ack_suggestion`，记录了处置与理由。 |
| `expired` | 超过 `suggestionTtlMs` 仍未投递。 |
| `cancelled` | 用户/主 Agent 在投递前撤回。 |

投递后 activation 结束仍未 ack 的，标记 `delivered` 并在 `team_finish` 结果里列入 `unacknowledgedSuggestions`；主 Agent 可据此提醒用户，但不自动判失败。

### 4.3 数据结构

`state/human.json` 中的建议记录：

```json
{
  "id": "sug_01J...",
  "teamId": "product-delivery",
  "target": {
    "agentId": "builder",
    "pipelineId": "delivery",
    "nodeId": "builder",
    "activationId": null
  },
  "source": {
    "kind": "user",
    "viaAgentId": "team-master",
    "sessionId": "sess_main_...",
    "userId": null
  },
  "text": "优先修登录，不要先做样式。",
  "intent": "feedback",
  "delivery": "queue",
  "status": "queued",
  "createdAt": "2026-02-01T09:50:00.000Z",
  "expiresAt": "2026-02-01T10:50:00.000Z",
  "deliveredAt": null,
  "deliveredIn": null,
  "acknowledgedAt": null,
  "acknowledgement": null
}
```

`intent` 取值：`constraint` / `feedback` / `requirement-change` / `question`。它只用于展示与筛选，不改变投递语义。

`acknowledgement`：

```json
{
  "disposition": "partially-accepted",
  "reason": "登录优先已采纳；样式改动属于本轮验收范围，仍会完成最小样式。",
  "at": "2026-02-01T10:05:00.000Z"
}
```

### 4.4 投递时机

| 配置/场景 | 行为 |
|---|---|
| `suggestionDelivery = queue`（默认） | 不唤醒 agent；在下一次 activation 消息中作为 `[team:suggestion]` 段交付。 |
| `suggestionDelivery = steer` 且 agent 正在执行 activation | 通过 `agent.steer` 注入当前回合，标记 `delivered`。 |
| `suggestionDelivery = steer` 但 agent 空闲 | 降级为 `queue`，工具结果里返回 `effectiveDelivery: "queue"`。 |
| 建议指定了 `activationId` 且该 activation 已结束 | 返回 `STALE_ACTIVATION`，由主 Agent 告知用户；不静默转给下一次。 |
| 建议指定了 `pipelineId`/`nodeId`，目标 agent 当前不在该 placement | 仍可排队，但只在该 placement 的下一次 activation 交付；面板标记“等待匹配 placement”。 |

一次 activation 可以带多条建议，按 `createdAt` 升序；总量受 `maxPendingSuggestionsPerAgent` 限制。

### 4.5 worker 如何回应

activation 消息中出现：

```text
[team:suggestion id=sug_01J... from=user via=team-master created=...]
优先修登录，不要先做样式。
[/team:suggestion]
```

worker 应当：

1. 在本次工作中考虑建议；
2. 调用 `team_ack_suggestion` 记录处置（推荐）；
3. 如果拒绝，给出可验证的理由，不静默忽略；
4. 不把建议当成新的 channel 或 artifact。

`team_ack_suggestion` 参数：

```json
{
  "suggestionId": "sug_01J...",
  "disposition": "accepted",
  "reason": "本轮先修登录，样式保持最小改动。"
}
```

### 4.6 工具

worker：

| 工具 | 说明 |
|---|---|
| `team_ack_suggestion` | 回应一条已投递建议；幂等。 |
| `team_get_context` | 返回当前 placement、本次输入、pending/delivered 建议。 |

主 Agent：

| 工具 | 说明 |
|---|---|
| `team_send_suggestion` | 创建建议；参数 `agentId`、`text`、可选 `pipelineId`/`nodeId`/`activationId`、`intent`、`delivery`。 |
| `team_list_suggestions` | 按 agent/状态筛选，返回投递与 ack 情况。 |
| `team_cancel_suggestion` | 撤回尚未投递的建议。 |

控制台/面板也可以创建建议，但必须走同一 Host 服务与同一套校验；不直接写状态文件。

## 5. 提问（Question）

### 5.1 语义

worker 在 activation 中遇到必须由用户决定、且无法从输入/团队名册/已有交付物推断的问题时，调用 `team_ask_user`。v1 的提问一律 **blocking**：activation 进入 `waiting_human`，直到回答、超时或取消。

不要用提问做这些事：

- 问队友能回答的问题（用团队内消息/现有交付物）；
- 问验收标准里已经写明的内容；
- 把“请确认我做得对”当提问；
- 一次抛出多个不相关的问题。拆成多次或合并成一个决策。

### 5.2 生命周期

```text
pending → answered → delivered → closed
   ↘ expired
   ↘ cancelled
```

| 状态 | 含义 |
|---|---|
| `pending` | 已创建，等待主 Agent/用户回答。 |
| `answered` | 主 Agent 已提交回答，尚未送达 worker。 |
| `delivered` | 回答已注入 worker 会话。 |
| `closed` | 对应 activation 已结束或 worker 已确认收到。 |
| `expired` | 超过 `questionTimeoutMs`。 |
| `cancelled` | worker 撤回，或 run 被停止。 |

### 5.3 数据结构

```json
{
  "id": "q_01J...",
  "teamId": "product-delivery",
  "askedBy": {
    "agentId": "analyst",
    "sessionId": "sess_analyst_...",
    "pipelineId": "delivery",
    "nodeId": "analyst",
    "runId": "run_01J...",
    "activationId": "act_01J..."
  },
  "kind": "decision",
  "question": "首版是否必须支持离线模式？",
  "context": "规格里的验收标准要求“无网络可用”，但实现成本会翻倍。",
  "options": [
    { "id": "yes", "label": "必须支持", "description": "首版即做离线缓存与冲突合并。" },
    { "id": "no", "label": "暂不支持", "description": "首版在线优先，离线列入后续。" }
  ],
  "allowFreeText": true,
  "status": "pending",
  "createdAt": "2026-02-01T10:00:00.000Z",
  "deadlineAt": "2026-02-01T10:30:00.000Z",
  "answeredAt": null,
  "answer": null,
  "deliveredAt": null,
  "closedAt": null
}
```

回答：

```json
{
  "text": "首版不做离线，但要在规格里写清楚后续范围。",
  "optionId": "no",
  "answeredByAgentId": "team-master",
  "answeredBySessionId": "sess_main_...",
  "at": "2026-02-01T10:12:00.000Z"
}
```

### 5.4 流程

1. worker 调用 `team_ask_user`。
2. 引擎校验：当前 activation、pending 上限、问题非空；写入 `pending`，activation 置 `waiting_human`，记录 `question.created`。
3. 引擎向主 Agent 会话投递 `[team:question]` 通知；主 Agent 若忙，消息排队，但不阻塞其他 agent。
4. 主 Agent 把问题转述给用户；用户回答后，主 Agent 调用 `team_answer_question`。
5. 引擎记录 `answered`，向 worker 投递 `[team:answer]`，activation 回到 `running`，worker 继续同一回合或下一回合。
6. worker 收到回答后继续；结束时正常 `team_finish`。问题置 `closed`。

如果 worker 在提问后回合已经结束（blocking 语义下引擎会保持 activation 打开），回答到达时通过 `agent.send(..., "next-turn", wakeup=true)` 唤醒。

### 5.5 超时

`questionTimeoutMs` 到期后按 `onQuestionTimeout`：

| 值 | 行为 |
|---|---|
| `cancel`（默认） | 问题置 `expired`，向 worker 发送 `TEAM_QUESTION_EXPIRED`，activation 恢复；worker 可基于显式假设继续，或 `team_finish(blocked)`。 |
| `notify` | 只提醒主 Agent 与面板，问题保持 pending；仍受 activation 自身 timeout 约束。 |
| `fail-activation` | 当前 activation 判失败，按 node 的 `retry` / `onFailure` 处理。 |

超时不是“用户已同意”。worker 不得把超时当成默认答案；若继续，必须在输出里写明假设。

### 5.6 并发与限制

- 每 agent 同时 pending 上限：`maxPendingQuestionsPerAgent`，默认 1；超过时 `team_ask_user` 返回 `QUESTION_LIMIT`。
- 同一 activation 只能有一个 blocking 提问；worker 要问第二件事，先结束当前问题。
- 主 Agent 可以同时持有多个 worker 的提问；面板按 deadline 排序。
- 提问不会暂停其他 agent；只暂停发起它的 activation。

### 5.7 工具

worker：

| 工具 | 说明 |
|---|---|
| `team_ask_user` | 创建 blocking 提问；返回 `questionId`、`deadlineAt`。 |
| `team_question_status` | 查询自己提问的状态与回答；用于恢复/重连。 |
| `team_cancel_question` | 撤回尚未回答的提问；activation 恢复为 running。 |

主 Agent：

| 工具 | 说明 |
|---|---|
| `team_list_questions` | 默认列 pending/answered；可按 agent、run 筛选。 |
| `team_get_question` | 读取完整问题、上下文、选项、deadline。 |
| `team_answer_question` | 提交回答；幂等键 `questionId`。 |
| `team_cancel_question` | 用户明确不回答时取消，并说明原因。 |

### 5.8 主 Agent 自己的提问

主 Agent 与用户在同一会话里，直接说话即可，不需要 `team_ask_user`。它不应创建针对自己的 Question；引擎拒绝 `askedBy.agentId === masterAgentId`。

## 6. 消息模板

### 6.1 给主 Agent 的提问通知

```text
[team:question id=q_01J...]
来自：analyst（delivery/analyst，run run_01J...，第 1 轮）
类型：decision
截止：2026-02-01T10:30:00.000Z

问题：首版是否必须支持离线模式？
```

## 7. 状态、事件与恢复

`state/human.json` 保存未终结的建议/提问索引：

```json
{
  "version": 1,
  "suggestions": {},
  "questions": {},
  "updatedAt": "2026-02-01T10:00:00.000Z"
}
```

事件追加到对应 run 的 `events.jsonl`：

- `suggestion.created` / `suggestion.delivered` / `suggestion.acknowledged` / `suggestion.expired` / `suggestion.cancelled`
- `question.created` / `question.notified` / `question.answered` / `question.delivered` / `question.expired` / `question.cancelled` / `question.closed`
- `human.direct-input`（用户直接对绑定会话说话时记录 sessionId/messageId/摘要，不记录消息正文）

恢复：

- 引擎重启后，`pending` 且 activation 仍存活的提问保持 pending，并重新通知主 Agent（去重，避免重复打扰）。
- activation 已不存在的 pending 提问置 `cancelled`，原因 `activation-lost`。
- `answered` 但未 `delivered` 的回答在恢复后重投；worker 侧按 `questionId` 幂等。
- `queued` 建议在 TTL 内继续有效；过期统一扫描。

## 8. HTTP 与 UI 契约

`GET /dsh-workspace-team/api/binding?sessionId=...` 增加：

```json
{
  "bound": true,
  "binding": {
    "kind": "worker",
    "managed": true,
    "placementState": "waiting_human"
  },
  "ui": { "composer": "blocked" },
  "human": {
    "mainAgent": {
      "agentId": "team-master",
      "name": "团队主 Agent",
      "sessionId": "sess_main_..."
    },
    "pendingQuestions": 1,
    "pendingSuggestions": 0
  }
}
```

主 Agent 会话：

```json
{
  "binding": { "kind": "front-desk", "managed": true },
  "ui": { "composer": "open" },
  "human": {
    "pendingQuestions": 2,
    "oldestDeadlineAt": "2026-02-01T10:30:00.000Z"
  }
}
```

`ui.composer` 只是状态：`blocked` 表示 Client 应设置 composer block，`open` 表示保持可输入。block 的 `reason` 文案由 Client 本地化，Host 不下发 UI 文案。

`GET /dsh-workspace-team/api/questions?status=pending` 与 `GET /dsh-workspace-team/api/suggestions?...` 供团队面板使用；写操作只通过工具或 Host 服务，不提供任意前端写接口。

## 9. 权限与审计

- 只有主 Agent 能调用 `team_send_suggestion` / `team_answer_question` / `team_cancel_question`；其他会话调用返回 `NOT_MAIN_AGENT`。
- 只有 worker 能调用 `team_ask_user` / `team_ack_suggestion` / `team_cancel_question`（自己的提问）；主 Agent 调用返回 `NOT_WORKER`。
- 回答通常来自主 Agent 会话；若 API/其他客户端在 worker 会话直接回复 pending Question（Web UI 默认 blocked），引擎观察该 user-role 消息并标记 `answer.source="direct"`，记录 `answeredBySessionId` 为 worker 会话，不信任客户端自报。
- 建议与回答正文可能含敏感信息；默认只存摘要与 hash 到事件日志，正文存 `state/human.json` 或 run artifacts，按 `retainRuns` / `retainDays` 清理。
- 审计视图能回答：谁在什么时候、通过哪个主 Agent 会话、对哪个 worker/activation 说了什么，以及 worker 是否回应。

## 10. 失败与边界

| 情况 | 行为 |
|---|---|
| 主 Agent 会话不存在/已释放 | 引擎进入 `degraded`；worker 提问仍可创建但无法通知，面板告警；超过 timeout 按 `onQuestionTimeout`。 |
| 主 Agent 正在执行长回合 | 提问通知排队；不阻塞其他 agent；deadline 照常计时。 |
| 用户关闭主 Agent 会话 | 绑定仍在；重新打开可继续；未回答提问保持 pending。 |
| worker 在提问后崩溃 | activation 失败；问题置 `cancelled`，原因 `worker-lost`。 |
| 回答到达时 activation 已结束 | 返回 `QUESTION_NOT_WAITING`，不把回答注入新 activation；主 Agent 告知用户。 |
| 同一问题重复回答 | 幂等：已 answered/closed 的返回当前状态，不覆盖首个回答。 |
| 建议目标 agent 不存在 | `team_send_suggestion` 返回 `UNKNOWN_AGENT`。 |
| 建议/提问跨团队 | 拒绝；v1 一个工作区只有一个团队。 |
| API/其他客户端直接给 worker 发消息（Web UI 默认 blocked） | 不拒绝；记录 `human.direct-input`（摘要）；若有 pending Question 则视为回答并知会主 Agent；否则只知会，不改变 activation。 |

## 11. 与旧 `humanChat` 的差异

v1 删除 `settings.humanChat`。旧语义与新语义的映射：

| 旧值 | 新行为 |
|---|---|
| `allow` | Host 仍不拦截；Web UI 默认 `workerComposer=blocked`；改成 `open` 才恢复直接输入。团队级建议仍推荐经主 Agent。 |
| `deny` | v1 不支持 Host 级“禁止直接对话”；用 `workerComposer=blocked` 表达 UI 默认禁用。 |
| `steer` | 由 `humanInteraction.suggestionDelivery = "steer"` 取代，只影响主 Agent 转发的建议如何投递。 |

迁移：加载器遇到 `humanChat` 直接报错（`additionalProperties: false`），错误信息提示改用 `settings.humanInteraction`；不静默忽略。

## 12. 示例时序

```text
用户 → 主 Agent：登录优先，不要先做样式。

引擎 → builder：activation 消息附带 [team:suggestion]
builder：执行，team_ack_suggestion(partially-accepted)
builder → 引擎：team_submit_artifact(review)
...
builder：team_ask_user("首版是否支持离线？")
引擎：activation → waiting_human；通知主 Agent
主 Agent → 用户：analyst 问……（转述）
用户 → 主 Agent：首版不做离线
主 Agent → 引擎：team_answer_question(q_1, "首版不做离线...")
引擎 → builder：[team:answer]
builder：继续并 team_finish

# 直接路径（仅 API/其他客户端/workerComposer=open；Web UI 默认无法这样输入）

引擎：记录 human.direct-input；不改变 activation，不生成 suggestion/artifact。

```
