# 团队配置文件字段规范（v1）

> 状态：设计草案。机器可读定义见 [schema/team.schema.json](../schema/team.schema.json)，完整示例见 [examples/team.json](../examples/team.json)。
>
> 本文回答三个问题：**每个字段是什么意思、默认值是什么、加载器在运行时怎么用它。**
>
> 消息内容见 [节点激活消息契约](./节点激活消息契约.md) 与 [智能体初始化消息契约](./智能体初始化消息契约.md)。

## 1. 文件位置与加载

一个工作区最多一个团队。配置文件固定为：

```text
<workspace>/.dsh/.dsh-workspace-team/team.json
```

同目录下可选：

```text
.dsh/.dsh-workspace-team/
├── team.json
├── schemas/           # channel 引用的 JSON Schema
├── prompts/           # agent / node 引用的提示词文件
├── state/             # 运行时状态（bindings、engine lock 等）
└── runs/              # 每次 pipeline run 的交付物与事件日志
```

- `team.json`、`schemas/`、`prompts/` 是**源文件**，建议提交到 git。
- `state/`、`runs/` 是**运行时产物**，建议 gitignore。
- `team.json` 内所有 `file` 路径都相对 `.dsh/.dsh-workspace-team/` 解析，并做路径逃逸检查。
- `external file sink` 的 `path` 是例外：它相对**工作区根目录**解析。

加载顺序：读取 JSON → JSON Schema 校验 → 语义校验（见第 8 节）→ 编译交付物 Schema → 解析提示词文件 → 构建图 → 启动/重载引擎。任何一步失败都不会部分生效。

## 2. 顶层结构

```json
{
  "schemaVersion": 1,
  "id": "product-delivery",
  "name": "产品交付团队",
  "description": "可选",
  "settings": {},
  "agents": [],
  "channels": [],
  "pipelines": []
}
```

| 字段              | 类型   | 必填 | 说明                                                 |
| ----------------- | ------ | ---- | ---------------------------------------------------- |
| `schemaVersion` | `1`  | 是   | 目前只接受 1。破坏性变更递增，加载器负责迁移或拒绝。 |
| `id`            | id     | 是   | 团队 id，小写 kebab-case，工作区内唯一。             |
| `name`          | string | 是   | 展示名。                                             |
| `description`   | string | 否   | 展示与系统提示词用，不参与调度。                     |
| `settings`      | object | 否   | 引擎、存储、会话、人类对话策略。                     |
| `agents`        | array  | 是   | 至少 1 个。                                          |
| `channels`      | array  | 是   | 至少 1 个。channel 就是图的边。                      |
| `pipelines`     | array  | 是   | 至少 1 个。                                          |

**没有单独的 `edges` 数组。** channel 既是 1:1 的交接契约，也是有向边；node 的入通道/出通道由 channel 的 `from`/`to` 反向推导，避免三处重复。

## 3. settings

```json
{
  "engine": {
    "provisioning": "eager",
    "maxConcurrentActivations": 4,
    "defaultNodeTimeoutMs": 1800000,
    "idleGraceMs": 60000,
    "resumeInterrupted": "mark-failed"
  },
  "storage": {
    "maxArtifactBytes": 1048576,
    "maxInlineBytes": 65536,
    "retainRuns": 100,
    "retainDays": 30
  },
  "session": {
    "titleTemplate": "{{team.name}} / {{agent.name}}"
  },
  "masterAgent": {
    "id": "team-master",
    "name": "团队主 Agent",
    "permission": "read-only"
  },
  "humanInteraction": {
    "workerComposer": "blocked",
    "suggestionDelivery": "queue",
    "suggestionTtlMs": 3600000,
    "questionTimeoutMs": 1800000,
    "onQuestionTimeout": "cancel",
    "maxPendingQuestionsPerAgent": 1,
    "maxPendingSuggestionsPerAgent": 8
  }
}
```

| 字段                                | 类型                                           | 默认                               | 说明                                                                                         |
| ----------------------------------- | ---------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------- |
| `engine.provisioning`             | `eager` \| `lazy`                          | `eager`                          | eager：`team up` 时初始化全部 agent 会话；lazy：节点第一次激活时才建会话。                 |
| `engine.maxConcurrentActivations` | int 1–32                                      | `4`                              | 引擎全局并发 activation 上限。                                                               |
| `engine.defaultNodeTimeoutMs`     | int                                            | `1800000`                        | node 未配置 `timeoutMs` 时的超时。                                                         |
| `engine.idleGraceMs`              | int                                            | `60000`                          | agent 回合结束但未 `team_finish` 时，先提醒；超过该时间判失败。                            |
| `engine.resumeInterrupted`        | `never` \| `redispatch` \| `mark-failed` | `mark-failed`                    | 引擎重启时如何处理中断的 activation。                                                        |
| `storage.maxArtifactBytes`        | int                                            | `1048576`                        | 单个交付物硬上限，channel 的 `maxBytes` 不得超过它。                                       |
| `storage.maxInlineBytes`          | int                                            | `65536`                          | 注入 activation 消息的内联内容上限。                                                         |
| `storage.retainRuns`              | int                                            | `100`                            | 最多保留多少次 run 的产物。                                                                  |
| `storage.retainDays`              | int                                            | 无                                 | 产物保留天数；与 retainRuns 先到先删。                                                       |
| `session.titleTemplate`           | string                                         | `{{team.name}} / {{agent.name}}` | 创建 agent 会话时的标题模板。                                                                |
| `masterAgent.id`                 | id                                             | `team-master`                    | 引擎生成的主 Agent id；不得与任何用户配置的 agent id 重复。                                   |
| `masterAgent.name`               | string                                         | `团队主 Agent`                   | 生成的主 Agent 展示名。                                                                       |
| `masterAgent.preset`             | string                                         | `standard`                       | 主 Agent 会话的 DSH agent preset；缺省 standard，团队工具与提示词叠加其上。                    |
| `masterAgent.permission`         | string                                         | `read-only`                      | 主 Agent 会话的 permission preset。                                                           |
| `masterAgent.model`              | object                                         | 会话默认                           | 主 Agent 的模型；缺省与会话默认一致。                                                         |
| `masterAgent.systemPrompt`       | textSource                                     | 内置主 Agent 协议                  | 可选的额外角色提示词；引擎仍会追加 roster、建议与提问工具说明。                               |
| `masterAgent.session`            | object                                         | `{{team.name}} / 主 Agent`       | 主 Agent 会话标题覆盖。                                                                       |
| `humanInteraction.workerComposer` | `blocked` \| `open`                 | `blocked`                        | Web UI 是否禁用绑定 worker 的输入框：blocked 调用 `ctx.conversation.blocks` 置为 inert；open 保持可输入。只影响 Web UI，Host 不拦截。 |
| `humanInteraction.suggestionDelivery` | `queue` \| `steer`                    | `queue`                          | 用户建议默认随下一次 activation 交付；`steer` 才尝试注入当前回合。                        |
| `humanInteraction.suggestionTtlMs` | int 60000–604800000                          | `3600000`                        | 建议未交付/未确认的存活时间；过期后不再投递。                                                |
| `humanInteraction.questionTimeoutMs` | int 60000–604800000                        | `1800000`                        | worker 提问的默认等待时间，超时按 `onQuestionTimeout` 处理。                                |
| `humanInteraction.onQuestionTimeout` | `cancel` \| `notify` \| `fail-activation` | `cancel`                      | 提问超时：撤回提问 / 仅通知主 Agent / 让当前 activation 失败。                                |
| `humanInteraction.maxPendingQuestionsPerAgent` | int 1–4                             | `1`                              | 单个 worker 同时未回答提问的上限。                                                           |
| `humanInteraction.maxPendingSuggestionsPerAgent` | int 1–64                          | `8`                              | 单个 worker 排队中建议的上限。                                                               |

## 4. agents

```json
{
  "id": "analyst",
  "name": "分析师",
  "role": "需求分析与规格撰写",
  "team_role": "slave",
  "description": "可选",
  "preset": "standard",
  "permission": "workspace-write",
  "model": { "provider": "deepseek", "model": "deepseek-chat", "reasoningEffort": "high" },
  "systemPrompt": { "file": "prompts/analyst.md" },
  "receivers": [
    { "id": "intake", "rule": ["brief"] }
  ],
  "session": { "title": "{{team.name}} / {{agent.name}}" },
  "bootstrap": { "mode": "wake", "message": "可选补充说明" }
}
```

| 字段                  | 类型                   | 必填 | 默认              | 说明                                                                                                                                                                 |
| --------------------- | ---------------------- | ---- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                | id                     | 是   | —                | 团队内唯一。                                                                                                                                                         |
| `name`              | string                 | 是   | —                | 展示名；同名不禁止，但 id 必须唯一。                                                                                                                                 |
| `role`              | string                 | 是   | —                | 一句话角色，进入 roster。                                                                                                                                            |
| `team_role`         | `master` \| `slave` | 否   | `slave`        | 用户配置只能省略或写 `slave`；`master` 由引擎生成，手写会被 validator 拒绝。                                                                                       |
| `description`       | string                 | 否   | —                | 更长的职责说明，进入 roster。                                                                                                                                        |
| `preset`            | string                 | 否   | `standard`      | 该 agent 使用的 DSH agent preset 名称；可为任意已安装 preset，团队工具与提示词叠加其上。schema 不再 `const`。                                                    |
| `permission`        | string                 | 否   | 部署默认          | DSH 会话 permission preset 的**名称**（如 `read-only` / `workspace-write` / `danger-full-access`，也可由部署自定义）。preset 解析为 sandbox + approval。 |
| `model`             | object                 | 否   | 会话默认          | `model` 必填；`provider`、`reasoningEffort` 可选。                                                                                                             |
| `systemPrompt`      | textSource             | 是   | —                | 工作区级角色/领域提示词，只写身份、职责与约束；引擎会在其后追加内置团队协议和该 agent 的可用输出通道。文件相对配置目录。 |
| `receivers`         | receiver[]             | 否   | `[]`            | 该 agent 的接收器。每个接收器只有一条规则（channel id 数组）；不同接收器独立满足、先到先激活。                                                                     |
| `session.title`     | string                 | 否   | settings 里的模板 | 该 agent 的会话标题覆盖；每个 agent 恰好一个会话。                                                                                                                   |
| `bootstrap.mode`    | `wake` \| `silent` | 否   | `wake`          | wake：初始化时发 standby 消息并让 agent 回 READY；silent：只写系统提示词，不产生回合。                                                                               |
| `bootstrap.message` | string                 | 否   | —                | 追加到默认 standby 消息之后。                                                                                                                                        |

- **textSource**：`{ "inline": "..." }` 或 `{ "file": "prompts/x.md" }`，二选一。
- **一个 agent 一个会话**：agent 与真实 DSH 会话是 1:1，不提供 per-run 会话。agent 被多个 node 复用时，复用的仍是同一个会话（因而上下文延续），激活按 per-agent FIFO 串行。若需要运行隔离，请定义独立 agent，而不是给同一 agent 开多个会话。
- **preset 可选，缺省 `standard`**：`agent.preset` 可为任意已安装的 DSH agent preset；引擎创建会话时原样传入。字段保留在 team.json 里，是为了让配置自描述、可审计、可恢复。DSH 的 agent preset 决定工具集、基础 persona/系统提示词和技能；团队自己的角色提示词和工具是叠加在它之上。agent preset 与 `permission`（permission preset）是两套独立机制：前者决定“加载什么”，后者决定“沙箱与审批”。未知 preset 使 provision 失败（`TEAM_PRESET_UNKNOWN`），不静默回退。
- **permission 是 preset 名，不是 sandbox 枚举**：DSH 的会话权限由部署的 permission preset 表定义，每个 preset 解析为 `{ sandbox, approval }`。team.json 只引用 preset 名称，不复制 sandbox/approval 组合；本部署常见名称是 `read-only` / `workspace-write` / `danger-full-access`，但 profile 可以增加自定义 preset。`auto` 仅在部署启用 Auto 集成时可用；`custom` 是派生状态，不能作为配置值。加载器在 Host 内用 `permissionPresets` catalog 解析，未知名称拒绝 provision，不静默降级。
- **系统提示词由四部分组成**：工作区角色（`agent.systemPrompt`）→ 内置通用团队协议（工具、调用方法、交付/完成规则）→ **可用输出通道**（按 placement 分组，引擎从 channel 图生成）→ roster。`systemPrompt` 只写角色/领域约束；不要把工具说明、团队协议或输出通道清单写进去，否则会与配置/引擎版本漂移。
- **主 Agent 是引擎生成的保留 agent**：用户不需要也不允许在 `agents` 中手写 `team_role: "master"`。引擎初始化时按 `settings.masterAgent` 生成/补齐一个 `team_role=master` 的 agent，写入运行时有效配置和 `state/master.json`，不修改用户的 `team.json`。它不得被任何 pipeline node 引用，不得定义 `receivers`，只装主 Agent 工具（建议转达、提问代办、只读状态），不接收 activation。其余 agent 都是 `team_role=slave` 的 worker，仍是普通 DSH 会话；Web UI 默认用 composer block 禁用其输入框（`humanInteraction.workerComposer=blocked`），用户经主 Agent 提建议/回答；API/其他客户端或 `workerComposer=open` 时仍可直接输入。主 Agent 只是推荐前台，Host 不拦截 `session.prompt`。
- **有效配置恰好一个 master**：加载后的运行时 roster = 用户配置的 slave agents + 引擎生成的 master。生成 id 默认 `team-master`，可用 `settings.masterAgent.id` 覆盖，但不得与任何用户 agent id 冲突。

### 4.1 receivers / rule

每个 agent 可以有多个接收器；每个接收器只有一条接收规则，规则是一个 channel id 数组。

```json
"receivers": [
  {
    "id": "spec-inbox",
    "name": "规格接收器",
    "rule": ["spec"]
  },
  {
    "id": "rework-inbox",
    "name": "返工接收器",
    "rule": ["review"]
  }
]
```

| 字段                   | 类型     | 必填 | 默认    | 说明                                                                 |
| ---------------------- | -------- | ---- | ------- | -------------------------------------------------------------------- |
| `receiver.id`          | id       | 是   | —      | agent 内唯一；channel 的 `to.receiverId` 引用它。                  |
| `receiver.name`        | string   | 否   | —      | 展示名。                                                             |
| `receiver.description` | string   | 否   | —      | 接收器用途说明。                                                     |
| `receiver.enabled`     | boolean  | 否   | `true` | false 时该接收器不参与激活评估。                                     |
| `receiver.rule`        | id[]     | 是   | —      | 接收规则：至少一个 channel id，不得重复。                            |

语义：

1. **规则是合取**：`rule` 里的每个 channel 都必须有未消费的合格交付物，这个接收器才满足。没有 `all/any/quorum` 模式。
2. **一个接收器只有一条规则**：需要“多种组合”时，定义多个接收器，每个接收器一条规则。
3. **先满足先激活，后到排队**：不同接收器独立评估；谁先满足，谁先产生 activation 请求。请求进入该 agent 的 FIFO，和用户消息一样按顺序处理，不会因为“优先级”丢弃后满足的接收器。
4. **原子消费**：某个接收器满足时，对 `rule` 里的每个 channel 各取队首一份，作为一个 activation 的完整输入；这些交付物同时标记为已消费。
5. **接收器绑定一个节点**：channel 的 `to` 指定 `pipelineId` / `nodeId` / `receiverId`；同一个 receiver 不能被两个节点同时使用。
6. **无入通道的节点不需要接收器**：它由 pipeline start 触发一次（典型是单节点 audit）。
7. **禁用的接收器不参与评估**：`enabled=false` 时它的规则被忽略。
8. **规则不能为空**：`rule` 至少一个 channel；一个“什么都不等”的规则会导致无限激活。

## 5. channels

channel 是**带类型契约的 1:1 有向边**。`from` 是唯一生产者，`to` 是唯一消费者；扇出要建多条 channel。

```json
{
  "id": "spec",
  "name": "需求规格",
  "from": { "kind": "node", "pipelineId": "delivery", "nodeId": "analyst" },
  "to":   { "kind": "receiver", "pipelineId": "delivery", "nodeId": "builder", "receiverId": "spec-inbox" },
  "artifact": {
    "kind": "json",
    "schema": "schemas/spec.schema.json",
    "schemaDialect": "2020-12",
    "maxBytes": 131072
  },
  "required": true,
  "acceptance": [
    { "pointer": "/acceptanceCriteria", "op": "min-length", "length": 1 }
  ],
  "when": [],
  "delivery": {
    "inline": "auto",
    "maxInlineBytes": 65536
  },
  "retention": { "keepLast": 10 }
}
```

| 字段                                  | 类型                               | 必填 | 默认            | 说明                                                                                                     |
| ------------------------------------- | ---------------------------------- | ---- | --------------- | -------------------------------------------------------------------------------------------------------- |
| `id`                                | id                                 | 是   | —              | 团队内唯一。                                                                                             |
| `name` / `description`            | string                             | 否   | —              | 展示与投递消息用。                                                                                       |
| `enabled`                           | boolean                            | 否   | `true`        | false 时该边不参与调度，但配置仍保留。                                                                   |
| `from`                              | producerParty                      | 是   | —              | 生产者：node 或 external/user。                                                                          |
| `to`                                | consumerParty                      | 是   | —              | 消费者：receiver 或 external/file。receiver 端点必须给出 pipeline/node/receiver。                         |
| `artifact`                          | artifact                           | 是   | —              | 交接物契约。                                                                                             |
| `required`                          | boolean                            | 否   | `true`        | **输出义务**：生产者 node 在 `team_finish` 前必须在该通道成功提交过交付物。互斥备选路径应标 `false`。external 生产者忽略。 |
| `acceptance`                        | predicate[]                        | 否   | `[]`          | **合格性**：不满足则拒绝提交，不产生 delivery。                                                    |
| `when`                              | predicate[]                        | 否   | `[]`          | **路由**：合格后才评估；全部满足才触发下游。空数组=总是触发。                                      |
| `delivery.inline`                   | `auto` \| `always` \| `path` | 否   | `auto`        | 注入 activation 消息时是否内联内容。                                                                     |
| `delivery.maxInlineBytes`           | int                                | 否   | settings 值     | 单通道内联上限。                                                                                         |
| `retention.keepLast` / `keepDays` | int                                | 否   | —              | 该通道交付物保留策略。                                                                                   |

**channel 是 1:1 的边**：一个 channel 恰好一个 `from`、一个 `to`；一个生产者要发给多个消费者，就建多条 channel。channel **不再声明“是否是激活必需输入”**；某个 channel 是否参与某次激活，完全由消费者节点的 receiver rule 决定。

**输出由 agent 自己选**：`to` 在配置里固定，但一次 activation 中走哪条（或多条）出通道，由 agent 根据当前情况决定——例如评审通过走 `publish`，打回走 `review`。引擎不在 activation 里预先指定输出，只把该节点全部出通道（类型、schema、目标、是否 required）写进系统提示词的「可用输出通道」段。因此：

- 同一 agent 在不同情境下可以交接给不同下游；
- 选择 channel 就等于选择目标 receiver/file，提交时仍显式给 `receiverId` + `channelId`（file 目标只给 `channelId`）；
- `required=true` 表示“这次 activation 完成前必须成功提交”，不是“每次都要走”。同一节点有多条互斥备选路径时，只把始终必经的那条标 `true`，其余标 `false`；不要把每条备选都标 required，否则 agent 无法只选一条。

### 5.1 producerParty

```json
{ "kind": "node", "pipelineId": "delivery", "nodeId": "analyst" }
```

或：

```json
{ "kind": "external", "source": "user" }
```

`external/user` 只用于 pipeline 启动时注入 brief。

### 5.2 consumerParty

receiver 端点：

```json
{
  "kind": "receiver",
  "pipelineId": "delivery",
  "nodeId": "builder",
  "receiverId": "spec-inbox"
}
```

- `nodeId` 决定这个接收器挂在哪个 pipeline 节点上；
- `receiverId` 决定由该节点 agent 的哪个接收器接；
- 引擎会校验：receiver 存在于该 node 的 agent、该 receiver 的 `rule` 包含这个 channel、同一个 receiver 不被两个 node 使用。

或 file sink：

```json
{ "kind": "external", "sink": "file", "path": "docs/final-report.md", "overwrite": true }
```

file sink 的 `path` 相对工作区根目录；引擎在交付物被接受后用原子写落盘。禁止写到 `.dsh/.dsh-workspace-team/` 内。v1 只支持 text 落盘；json 交付物请先转成文本，或等 v2 的文件 sink 类型。

**v1 限制**：`from` 是 node 且 `to` 是 receiver 时，两者必须属于同一个 pipeline。跨 pipeline 的边留到后续版本。

### 5.3 artifact

| 字段                        | 类型                        | 必填      | 说明                                                              |
| --------------------------- | --------------------------- | --------- | ----------------------------------------------------------------- |
| `kind`                    | `text` \| `json`        | 是        | 交付物类型。                                                      |
| `schema`                  | filePath                    | json 必填 | JSON Schema 文件，相对配置目录。text 不允许该字段。               |
| `schemaDialect`           | `2020-12` \| `draft-07` | 否        | 默认 `2020-12`。                                                |
| `mimeType`                | string                      | 否        | text 的提示性 MIME，如 `text/markdown`；不参与校验。            |
| `minBytes` / `maxBytes` | int                         | 否        | 字节数边界；maxBytes 不得超过 settings.storage.maxArtifactBytes。 |
| `title`                   | string                      | 否        | 展示名。                                                          |

JSON Schema 只允许本地 `$ref`，加载时会拒绝远程 `$ref` 和指向配置目录之外的引用。

### 5.4 acceptance / when predicate

```json
{ "pointer": "/status", "op": "eq", "value": "changes_requested" }
```

`pointer` 是 RFC 6901 JSON Pointer。text 交付物只允许空指针 `""`。

| op                              | 额外字段          | 语义                            |
| ------------------------------- | ----------------- | ------------------------------- |
| `eq` / `neq`                | `value`         | 深比较相等/不等。               |
| `in` / `not-in`             | `value` (array) | 值在/不在数组中。               |
| `exists` / `not-exists`     | —                | 指针存在/不存在。               |
| `matches`                     | `pattern`       | JS 正则匹配；pattern 长度受限。 |
| `min-length` / `max-length` | `length`        | 字符串长度或数组元素数。        |
| `min` / `max`               | `number`        | 数值边界。                      |

**acceptance 与 when 的区别**：acceptance 决定“这份交付物合不合格”，不合格会被工具拒绝、agent 可以修正后重提；when 决定“合格交付物要不要触发下游”，不满足时仍入库、记录为 filtered，但不产生 delivery。二者都不要拿来做权限判断。

## 6. pipelines

```json
{
  "id": "delivery",
  "name": "需求交付",
  "enabled": true,
  "start": {
    "mode": "manual",
    "entryNodes": ["analyst"],
    "briefChannel": "brief"
  },
  "nodes": [],
  "completion": {
    "mode": "all-terminal",
    "terminalNodes": ["reviewer"]
  },
  "budget": {
    "maxNodeRuns": 20,
    "maxWallClockMs": 7200000,
    "maxArtifacts": 40
  },
  "layout": { "analyst": { "x": 0, "y": 120 } }
}
```

| 字段                         | 类型                                 | 必填 | 默认             | 说明                                                                                             |
| ---------------------------- | ------------------------------------ | ---- | ---------------- | ------------------------------------------------------------------------------------------------ |
| `id`                       | id                                   | 是   | —               | 团队内唯一。                                                                                     |
| `name` / `description`   | string                               | 否   | —               | 展示与 activation 消息用。                                                                       |
| `enabled`                  | boolean                              | 否   | `true`         | false 时不能启动新 run。                                                                         |
| `start.mode`               | `manual` \| `auto`               | 否   | `manual`       | auto：team up 后自动启动一次。                                                                   |
| `start.entryNodes`         | id[]                                 | 是   | —               | 启动时视为已就绪的节点；其必需入通道必须已经没有未满足的 node 生产者（通常只接 external/user）。 |
| `start.briefChannel`       | id                                   | 否   | —               | 用户 brief 注入通道；必须 from external/user，to 是 entry node，且出现在该节点某个接收规则里。    |
| `completion.mode`          | `all-terminal` \| `any-terminal` | 否   | `all-terminal` | 终止节点完成策略。                                                                               |
| `completion.terminalNodes` | id[]                                 | 是   | —               | 终止节点；run 在终止条件满足且图静止时完成。                                                     |
| `budget.maxNodeRuns`       | int                                  | 否   | 引擎默认         | 整个 run 的激活总次数上限。                                                                      |
| `budget.maxWallClockMs`    | int                                  | 否   | 引擎默认         | 整个 run 的墙钟上限。                                                                            |
| `budget.maxArtifacts`      | int                                  | 否   | 引擎默认         | 整个 run 的交付物数量上限。                                                                      |
| `layout`                   | object                               | 否   | —               | 仅 UI 用的节点坐标。                                                                             |

### 6.1 node

```json
{
  "id": "builder",
  "name": "实现",
  "agentId": "builder",
  "instructions": { "inline": "..." },
  "activation": {
    "maxActivations": 4,
    "retry": { "maxAttempts": 2, "backoffMs": 5000 },
    "onFailure": "fail-pipeline"
  },
  "timeoutMs": 1800000,
  "position": { "x": 280, "y": 120 }
}
```

| 字段                             | 类型                                           | 必填             | 默认              | 说明                                                                    |
| -------------------------------- | ---------------------------------------------- | ---------------- | ----------------- | ----------------------------------------------------------------------- |
| `id`                           | id                                             | 是               | —                | pipeline 内唯一。                                                       |
| `name`                         | string                                         | 否               | —                | 展示名。                                                                |
| `agentId`                      | id                                             | 是               | —                | 必须引用存在的 agent。                                                  |
| `instructions`                 | textSource                                     | 否               | 空                | activation 任务说明；支持第 7 节变量。                                  |
| `activation.maxActivations`    | int                                            | 否               | 无限              | 单次 run 内该节点最多激活几次。有环图必须至少有一个环上节点设置有限值。 |
| `activation.retry.maxAttempts` | int 1–10                                      | 否               | `1`             | 失败后的总尝试次数（含第一次）。                                        |
| `activation.retry.backoffMs`   | int                                            | 否               | `0`             | 重试间隔。                                                              |
| `activation.onFailure`         | `fail-pipeline` \| `continue` \| `retry` | 否               | `fail-pipeline` | 节点失败后的流水线策略。                                                |
| `timeoutMs`                    | int                                            | 否               | settings 默认     | 单次 activation 超时。                                                  |
| `position`                     | point                                          | 否               | layout 中的值     | 仅 UI。                                                                 |

**node 的通道不在 node 上声明**。入通道 = 所有 `to.nodeId` 指向该 node 的 channel；出通道 = 所有 `from` 指向该 node 的 channel。这样 channel 是唯一事实来源。哪个入通道由哪个接收器接，写在 channel 的 `to.receiverId` 里。

### 6.2 零入通道的节点

没有任何入通道的节点没有接收器；它在 pipeline 启动时被触发一次。这是 `audit` 这类单节点流水线的正常写法。若它不是 entry node，则从 entry 不可达，加载时报错。

### 6.3 多个接收器的排队

同一个节点的 agent 可以有多个接收器，每个接收器有自己的规则：

```json
"receivers": [
  { "id": "spec-inbox", "rule": ["spec"] },
  { "id": "rework-inbox", "rule": ["review"] }
]
```

- `spec` 先到 → `spec-inbox` 满足 → 产生一个 activation，agent 开始做首次实现。
- 如果 `review` 随后到达 → `rework-inbox` 满足 → 再产生一个 activation，排在上一个后面。
- 如果两个接收器几乎同时满足 → 按满足时间入队；同一 agent 一次只执行一个 activation，后到的排队，不丢弃。

不存在“优先级更高的规则覆盖低优先级规则”的语义；接收器之间只有先后顺序。需要合并多个通道时，把通道放进同一个接收器的 `rule` 数组，而不是拆成多个接收器。

`instructions`、agent `systemPrompt`、`session.title` 支持以下变量：

| 变量                                                       | 含义                                       |
| ---------------------------------------------------------- | ------------------------------------------ |
| `{{team.id}}` / `{{team.name}}`                        | 团队。                                     |
| `{{agent.id}}` / `{{agent.name}}` / `{{agent.role}}` | 当前 agent。                               |
| `{{pipeline.id}}` / `{{pipeline.name}}`                | 当前 pipeline。                            |
| `{{node.id}}` / `{{node.name}}`                        | 当前 node。                                |
| `{{run.id}}`                                             | 当前 run。                                 |
| `{{activation.id}}`                                      | 当前 activation。                          |
| `{{activation.iteration}}`                               | 当前节点在本 run 的第几次激活，从 1 开始。 |

## 8. 语义校验清单

JSON Schema 只能保证结构。加载器还必须做以下检查；标 **(error)** 的会拒绝加载，标 **(warn)** 的只提示。

1. **(error)** `team.json` 位于 `.dsh/.dsh-workspace-team/`，一个工作区只有一个。
2. **(error)** 所有 agent / channel / pipeline id 唯一；node id 在 pipeline 内唯一；receiver id 在 agent 内唯一。
3. **(error)** `node.agentId` 指向存在的 agent；`from` 的 pipeline/node 与 `to` 的 pipeline/node/receiver 指向存在的对象。
4. **(error)** v1 中 `from` 是 node、`to` 是 receiver 时，两端必须在同一 pipeline。
5. **(error)** `start.entryNodes`、`completion.terminalNodes` 指向本 pipeline 的节点。
6. **(error)** `start.briefChannel` 必须 from external/user，`to` 是 entry node 上的某个 receiver。
7. **(error)** brief channel 必须出现在该 receiver 的 `rule` 里，否则 brief 永远不触发 activation。
8. **(error)** 每个 `to.receiverId` 必须存在于该 node 的 agent；同一 receiver 只能被一个 node 使用；channel 必须出现在该 receiver 的 `rule` 里；`rule` 里的每个 channel 必须指向同一个 receiver，且 receiver 所属 agent 与 node 的 agent 一致。
9. **(error)** 同一 pipeline 内，从 entry 沿 channel 可达所有节点；终止节点可达。
10. **(error)** 每个 SCC（含自环）必须有界：环上至少一个节点有有限 `maxActivations`，或 pipeline 的 `budget.maxNodeRuns` / `maxWallClockMs` 有限。
11. **(error)** json 通道的 schema 文件存在、可编译、只含本地 `$ref`；text 通道不得有 `schema`。
12. **(error)** 所有 `file` 路径在配置目录内，无 `..`、绝对路径、反斜杠、symlink 逃逸。
13. **(error)** file sink 路径在工作区内，且不在 `.dsh/.dsh-workspace-team/` 内。
14. **(error)** `artifact.minBytes <= maxBytes`，且 `maxBytes <= settings.storage.maxArtifactBytes`。
15. **(error)** 每个 `activation.maxActivations` 为正整数；每个 `retry.maxAttempts` 在 1–10。
16. **(warn)** 同一 agent 被多个 node 引用：合法，但 activation 会串行排队；每个 node 必须使用独立 receiver。
17. **(warn)** 没有任何 terminal 节点可达的节点；没有任何入通道且未列为 entry 的节点。
18. **(warn)** channel 的 `acceptance`/`when` 在 text 上使用了 `eq` 之类需要 JSON 的 op。
19. **(warn)** `start.mode=auto` 且 entry node 有必需 node 入通道：自动启动可能永远等不到输入。
20. **(warn)** agent 定义了 receiver，但没有任何 channel 指向它（规则永远不会满足）。
21. **(error，需 Host 上下文)** 若配置了 `agent.permission`，它必须存在于 Host 的 `permissionPresets` catalog；静态 validator 不加载 profile，跳过这一条。
22. **(error)** 生成的主 Agent id（`settings.masterAgent.id`，默认 `team-master`）不得与任何用户配置的 `agent.id` 冲突；该 id 不得被任何 pipeline node 的 `agentId` 引用。
23. **(error)** 用户配置的 agent 只能省略 `team_role` 或写 `slave`；写 `master` 直接拒绝，因为 master 由引擎生成，避免两个 master 或用户覆盖内置前台协议。

## 9. 运行时字段映射

| 配置                                 | 运行时行为                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `agent.preset`                     | `session.create` 时传入；缺省 `standard`；schema 不再 `const`。若 preset 不存在，provision 失败 `TEAM_PRESET_UNKNOWN`。 |
| `agent.permission`                 | 创建会话后按 Host 的 permission preset 切换；未知 preset 使 provision 失败。                    |
| `channel.acceptance`               | `team_submit_artifact` 时校验；失败返回校验错误，不入库、不投递。                             |
| `channel.when`                     | 合格交付物入库后评估；false 记为 filtered，不投递。                                             |
| `channel.from` / `channel.to`    | provision 时生成系统提示词「可用输出通道」段，按 placement 列出该节点全部出通道及固定目标；agent 自己选 channel。 |
| `channel.required`                 | 完成义务：`team_finish` 时检查该节点必需出通道是否都已成功提交；互斥备选标 false。             |
| `channel.to.receiverId`           | 投递目标接收器；必须匹配该 node 的 agent，且 channel 在该 receiver 的 `rule` 里。file 目标没有 receiverId。 |
| `agent.receivers[].rule`           | 该接收器满足的唯一条件：rule 里每个 channel 都有未消费的合格交付物。                             |
| 接收器满足                       | 产生一个 activation 请求并进入 per-agent FIFO；后满足的排队，不丢弃。                            |
| `team_submit_artifact`            | agent 自己选 channel：receiver 目标必须同时给 `receiverId` 与 `channelId`；file 目标只给 `channelId`。引擎校验 channel 属于当前节点且目标匹配后才入库。 |
| `delivery.inline` / `maxInlineBytes` | 决定 activation 消息里是否内联交付物内容。                                                       |
| `activation.maxActivations`        | 每次 run 的节点激活计数上限。                                                                   |
| `activation.retry` / `onFailure` | 节点失败后的重试与流水线策略。                                                                  |
| `completion`                       | 终止条件。                                                                                      |
| `budget`                           | run 级硬上限；超出后 run 以 `budget_exhausted` 结束。                                         |

## 10. 常见建模

**扇出**：一个 node 有多个出通道，分别指向不同下游；agent 按当前情况选择走哪条或哪几条，每条独立校验、独立投递。若要“每次都必须通知所有下游”，就把它们都标 `required=true`；若是条件分支，只把必经路径标 required。

**汇合**：一个 node 有多个入通道；把通道放进同一个 receiver 的 `rule: ["a", "b"]`，两个通道都有未消费交付物才满足，并一起交给 agent。

**多接收器排队**：同一 agent 的 `spec-inbox` 规则 `["spec"]`、`rework-inbox` 规则 `["review"]`；先到哪个就激活哪种任务。两个都到达时，先满足的先执行，后满足的排在同一个 agent 的 FIFO 后面。

**两种组合**：需要“code+tests 完整评审”和“只有 code 的快速路径”两种行为时，定义两个 receiver：
- `full-review`：`rule: ["code", "tests"]`
- `quick-review`：`rule: ["code"]`

通道先到哪组就触发哪个 receiver；不要试图在同一个 receiver 里写多条规则。

**有环反馈**：reviewer → builder 的 review 通道 + builder → reviewer 的 build-report 通道。必须给环上节点设 `maxActivations`，或给 pipeline 设 `maxNodeRuns`。评审通过/打回由 reviewer 自己选 `publish` 或 `review`，再用互斥的 `when` 兜底过滤。

**条件分支**：同一个 node 的多个出通道，agent 先按情境选 channel，再用互斥的 `when` 做引擎侧兜底过滤；不匹配的交付物入库但不投递。agent 的选路依据写在角色提示词里，不要指望 activation 替它决定。

**外部落盘**：`to: external/file`；适合最终报告、审计报告、生成物。写入是原子的，失败会重试并记录。

**人类在环**：`from: external/user` + `start.briefChannel`；用户在启动 run 时提供 brief。运行中的提问不是 channel，而是 worker 调用 `team_ask_user`，由主 Agent 代办（见 [人工交互契约](./人工交互契约.md)）。

**跨 pipeline**：v1 不支持 node→node 跨 pipeline；需要时用一个 pipeline 的 terminal 节点 + 另一个 pipeline 的 user brief 手工衔接，或等 v2 的 pipeline port。

## 11. 版本与扩展

- `schemaVersion` 是唯一的格式版本；新增可选字段不升版本，删除/改语义才升。
- 未识别的字段一律报错（`additionalProperties: false`），避免拼写错误静默生效。
- 预留但 v1 不实现的字段：pipeline port、channel 跨 pipeline、node 级 model 覆盖、artifact 二进制类型。
- 迁移策略：加载器按 `schemaVersion` 分派迁移函数，迁移后再次跑完整校验；迁移失败拒绝加载并给出原始错误。
