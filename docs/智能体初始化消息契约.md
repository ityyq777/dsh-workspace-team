# 智能体初始化消息契约

> 本文回答：**团队引擎初始化某个 agent 时，到底给这个 agent 发送什么内容。**
>
> 相关文档：[总体设计](./总体设计.md) · [团队配置文件字段规范](./团队配置文件字段规范.md) · [节点激活消息契约](./节点激活消息契约.md)

## 0. 先澄清“主 Agent”和“团队引擎”

本设计里有两个容易混淆的角色：

- **团队引擎**（Host 插件）：工作区级服务，负责发现配置、锁、创建会话、发 bootstrap、调度 activation。它不调用 LLM，不做自由决策，也不是一个对话 agent。
- **主 Agent**（`team_role=master`，由引擎自动生成，默认 id `team-master`）：一个**真实的 DSH 会话**，是用户推荐的前台。它转达用户建议、代办 worker 提问、解释团队状态；不执行 pipeline 节点，不接收 activation。用户不在 `team.json` 中手写它。

其余 agent 都是用户配置的 **worker**（`team_role=slave`）：被 pipeline node 引用，接收 activation。它仍是普通 DSH 会话，Host 允许直接对话；但 Web UI 默认禁用其 composer，用户经主 Agent 提建议或回答问题。

因此初始化消息有两套模板：worker 用第 3 节，主 Agent 用第 6.1 节。两者都由引擎按配置生成，不允许 LLM 自由改写。

## 1. 初始化时写入的两类内容

初始化分成两条通道，不要混：

| 通道 | 内容 | 生命周期 | 是否算“消息” |
|---|---|---|---|
| 系统提示词 | 工作区角色 + 内置团队协议 + 可用输出通道 + roster | 会话级，长期稳定 | 否，不进收件箱 |
| bootstrap 消息 | 身份、接收器、待命指令 | 一次性 | 是，user-role 消息 |

### 1.1 系统提示词（不是消息）

按固定顺序写入：

1. `agent.systemPrompt` + `role`：工作区定义的角色/职责/领域约束。
2. 内置团队协议：团队工具清单、调用方法、channel/交付/finish 规则、安全边界。
3. **可用输出通道**：该 agent 在每个 placement 下能提交的出通道、类型、是否 required、固定目标。引擎从 pipeline/channel 配置生成，按 `pipeline/node` 分组。
4. roster：团队与全部 agent 的静态名册。

这四段在会话创建时写入，之后每条 activation 不再重复。输出通道放在这里而不是 activation 里，是因为同一个 agent 在不同情况下可能选择不同下游；agent 执行时自己选 channel，而不是由 activation 预先规定。详见 [总体设计 8.3](./总体设计.md#83-系统提示词组成)。

### 1.2 bootstrap 消息（是消息）

bootstrap 是初始化后发给 agent 的**一条 user-role 会话消息**，以 `[team:bootstrap]` 开头。worker 的 bootstrap 只做三件事：

1. 告诉 agent 它是谁、属于哪个团队；
2. 告诉它有哪些接收器与规则；
3. 告诉它现在是 standby、不要开始任务，并要求它回一行 READY。

它**不包含** activation 任务、输入交付物、输出通道清单、run 目标或 node instructions。输出通道已经在系统提示词中给出，bootstrap 不重复。

## 2. 发送前置条件

只有以下步骤都成功，才发送 bootstrap：

1. 创建或复用真实会话，写入绑定账本（`provisioning`）。
2. 应用 agent 配置的 preset（缺省 `standard`）、permission preset、模型。
3. 安装该会话作用域的 team 工具。
4. 写入系统提示词三段。
5. 发送 bootstrap（`wake` 模式），等 READY；`silent` 模式跳过发送。

顺序不能反：**先写绑定，再发首条消息**。这样 `agent/created` 事件和工具安装都能查到绑定，崩溃恢复也能对账。

## 3. 消息模板

```text
[team:bootstrap] boot_01J...
protocol: 1
team: product-delivery (产品交付团队)
agent: builder (实现者)
role: 按规格实现并自测
workspace: /Users/yyq/code/example

placements:
- delivery/builder (实现)

receivers:
- spec-inbox (规格接收器): rule [spec]
- rework-inbox (返工接收器): rule [review]

teammates:
- team-master (团队主 Agent): 用户前台、建议转达与提问代办
- analyst (分析师): 需求分析与规格撰写
- reviewer (评审者): 代码与交付质量评审
- auditor (审计员): 依赖、配置与敏感信息审计

status: standby
activation: 只有收到 [team:activation] 才开始任务
input: ui-blocked

请只回复一行：
READY

不要开始任何任务；不要主动提交交付物；不要修改 .dsh/.dsh-workspace-team/。
```

## 4. 字段说明

| 字段 | 必填 | 含义 |
|---|---|---|
| `[team:bootstrap] boot_...` | 是 | 消息类型与 bootstrap id；用于日志、幂等和重试。 |
| `protocol` | 是 | 消息协议版本。 |
| `team` | 是 | 团队 id 与展示名。 |
| `agent` | 是 | 当前 agent id 与展示名。 |
| `role` | 是 | 一句话角色；与 `agent.role` 一致。 |
| `workspace` | 否 | 工作区绝对路径；方便 agent 确认边界。 |
| `placements` | 是 | 该 agent 被哪些 pipeline/node 使用；可能有多条。 |
| `receivers` | 是 | 每个接收器的 id、展示名和 rule 数组。 |
| `teammates` | 是 | 其他 agent 的 id、展示名、role，包含引擎生成的 master；完整 roster 在系统上下文。 |
| `status` | 是 | 初始化后固定为 `standby`。 |
| `activation` | 是 | 明确“只有 activation 才工作”。 |
| `input` | 是 | worker 为 `ui-blocked`：Web UI 禁用本会话输入框，用户经主 Agent 提建议/回答；Host 不拦截 API 输入。master 为 `open`。 |
| `READY` | 是 | 唯一认可的确认行。 |

## 6. 收到 READY 之后

1. 引擎把绑定状态从 `provisioning` 改为 `standby`。
2. 记录 `agent.ready` 事件。
3. 不派发任何任务；等待接收器满足。
4. worker 会话的 composer 在 Web UI 中默认 block；用户经主 Agent 以建议/回答形式转达。Host 仍允许 API 直接输入，引擎会记录 `human.direct-input` 并知会主 Agent。

如果 agent 没有回 READY：

- 超时（v1 使用引擎常量 60s；后续若暴露为配置，命名为 `settings.engine.bootstrapTimeoutMs`）后重试一次；
- 第二次仍失败 → 绑定标记 `failed`，记录诊断，不派发任务；
- 不允许把“随便一句回复”当作 READY；必须匹配独立一行 `READY`（大小写不敏感）。

### 6.1 主 Agent 的 bootstrap

主 Agent 由引擎按 `settings.masterAgent` 生成或补齐（`team_role=master`，默认 id `team-master`）。它也是真实会话，但初始化内容和 worker 不同：没有 placements/receivers，不进入 standby 等 activation，而是直接进入前台。

```text
[team:bootstrap] boot_01J...
protocol: 1
team: product-delivery (产品交付团队)
agent: team-master (团队主 Agent)
team_role: master
generated: true
role: 用户前台、建议转达与提问代办
workspace: /Users/yyq/code/example

teammates:
- analyst (分析师): 需求分析与规格撰写
- builder (实现者): 按规格实现并自测
- reviewer (评审者): 代码与交付质量评审
- auditor (审计员): 依赖、配置与敏感信息审计

status: front-desk
activation: 不接收 [team:activation]；只处理用户消息与 [team:question]
input: open
tools: team_status, team_list_agents, team_send_suggestion, team_list_suggestions,
       team_cancel_suggestion, team_list_questions, team_get_question,
       team_answer_question, team_cancel_question

请只回复一行：
READY

你是用户推荐的前台，不是唯一入口。不要执行节点任务，不要伪造 worker 的回答，不要把建议当命令。
```

主 Agent bootstrap 的额外规则：

- 不带 `placements` / `receivers`；它不属于任何 pipeline node。
- `team_role: master` 与 `generated: true` 表明它不在用户 `team.json` 中，是引擎补齐的保留 agent。
- `status` 固定 `front-desk`，不参与 activation 调度。
- `input: open`：主 Agent 的 composer 正常，用户可以直接对话。
- `tools` 只列主 Agent 工具；worker 工具（submit/finish/ask_user/ack）不安装。
- 用户消息、`[team:question]`、`[team:answer]` 由引擎按人工交互契约投递。

## 7. silent 模式

`bootstrap.mode = "silent"` 时不发送这条消息：

- 系统提示词、工具、绑定照常写入；
- agent 直接进入 `standby`；
- 第一次 activation 才验证模型、工具和权限；
- 适合大团队/成本敏感场景，但首次失败会更晚暴露。

## 8. 重启、复用与会话丢失

- **引擎重启**：已有绑定且会话仍存在 → 不重复 bootstrap；只对账，必要时发一条简短的 `[team:resume]`（v1 不实现，先记诊断）。
- **会话丢失**：原绑定标 `session-lost`；重新创建会话后，按本文完整 bootstrap 一次。
- **配置热重载**：agent 的角色/接收器/输出变化不追溯改写已存在会话的系统提示词；在静止点重建会话后才生效。
- **用户先聊过**：如果会话已存在且有历史，bootstrap 仍只发一次；不要把历史消息当成交付物。

## 9. 安全与隐私

bootstrap 里只放：

- 团队/agent/节点的名字与角色；
- 接收器规则；输出通道只在系统提示词，不在 bootstrap；
- 队友的名字与角色；
- 状态与操作约束。

不要放：

- 其他 agent 的 systemPrompt 全文；
- 任何 artifact 内容或用户 brief；
- API key、token、绝对敏感路径；
- 运行中的 activation 输入。

完整 roster 也按“名字 + 角色 + 节点”裁剪，不把整个 team.json 塞进消息。

## 10. 版本化

- `protocol: 1` 是 bootstrap 信封版本。
- 新增可选字段不升版本；改变 READY 语义、字段含义或删除字段才升版本。
- 旧会话不会自动获得新 bootstrap；升级后新会话使用新模板。
