# 节点激活消息契约

> 本文回答：**某个接收器满足规则、触发节点后，团队引擎到底给 agent 发送什么内容。**
>
> 相关文档：[总体设计](./总体设计.md) · [团队配置文件字段规范](./团队配置文件字段规范.md) · [智能体初始化消息契约](./智能体初始化消息契约.md)

## 1. 它是什么

activation 消息是引擎在一次 activation dispatch 时发给 agent 的**一条 user-role 会话消息**，以 `[team:activation]` 开头。它不是系统提示词，也不是普通用户聊天。

三个关键点：

1. **它是唯一授权**：agent 在 standby 阶段不工作；只有收到 `[team:activation]` 才开始本次任务。
2. **它对应一个接收器**：消息里固定带 `receiver` 和 `rule`，说明是哪条接收规则被满足。
3. **它是一次性任务上下文**：node instructions 与输入交付物在这条消息里；**输出通道不在这里**，它们在初始化时写入系统提示词，agent 按当前情况自己选择。

系统提示词（角色 + 内置团队协议 + 可用输出通道 + roster）在会话初始化时已经固定；activation 消息不重复粘贴系统提示词，只拼接本次任务所需的上下文。这样系统前缀稳定，KV cache 不会被每条 activation 打断。

## 2. 发送时机与队列

```text
channel FIFO 中有合格交付物
        │
        ▼
receiver.rule 的每个 channel 都有队首
        │
        ▼
该 receiver 满足，产生 activation 请求
        │
        ▼
进入该 agent 的 FIFO（先满足先入队）
        │
        ▼
agent idle ──► dispatch：原子消费输入，发送本消息
agent busy ──► 等待；消息不提前发送
```

- 不同 receiver 独立满足；后满足的排在同一个 agent 的 FIFO 后面，不丢弃。
- 同一 agent 一次只执行一个 activation。用户可以直接和任一团队会话聊天，包括 worker（Web UI 默认禁用 worker 输入框，API/其他客户端仍可直接输入）；用户消息是普通会话输入，不改变 activation 状态。主 Agent 同样不接收 activation。
- 消息只在真正 dispatch 时发送；排队中的 activation 不会先给 agent 发半套输入。
- 如果 dispatch 前 run 被暂停/取消，输入释放回 channel FIFO，消息不发送。

## 3. 消息模板

```text
[team:activation] act_01J...
protocol: 1
team: product-delivery (产品交付团队)
pipeline: delivery (需求交付)
node: builder (实现)
agent: builder (实现者)
run: run_01J...
iteration: 2 / 4
receiver: rework-inbox (返工接收器)
rule: [review]
queue: 前面还有 0 个待执行 activation
goal: 为 CLI 增加 --json 输出

inputs:
- channel: review (评审意见)
  artifact: art_01J...
  kind: json
  producer: delivery/reviewer (评审者)
  producedBy: act_01J...
  summary: 需要处理 2 个 blocker
  schema: schemas/review.schema.json
  schemaSha256: ...
  path: .dsh/.dsh-workspace-team/runs/.../content.json
  sha256: ...
  content: { ... }            # inline 策略允许时才有

# 如果有排队中的用户建议，追加（格式见《人工交互契约》4.5）：
[team:suggestion id=sug_01J... from=user via=team-master created=...]
优先修登录，不要先做样式。
[/team:suggestion]

# 这里不列出 outputs。可用输出通道及其目标在系统提示词「可用输出通道」段。

instructions:
<node.instructions 渲染结果>

completion:
- 按系统提示词中的可用输出通道，结合当前 node 与实际情况选择 channel
- 目标是 receiver 时同时给 receiverId 与 channelId
- 全部 required 输出被接受后调用 team_finish
- 不要修改 .dsh/.dsh-workspace-team/ 下的配置与状态文件
```

## 4. 字段说明

### 4.1 信封

| 字段                          | 必填 | 含义                                                                                   |
| ----------------------------- | ---- | -------------------------------------------------------------------------------------- |
| `[team:activation] act_...` | 是   | 消息类型与 activation id；用于幂等、日志、重放。                                       |
| `protocol`                  | 是   | 消息协议版本；引擎升级时用它判断兼容性。                                               |
| `team`                      | 是   | 团队 id 与展示名。                                                                     |
| `pipeline`                  | 是   | 当前 pipeline id 与展示名。                                                            |
| `node`                      | 是   | 当前节点 id 与展示名。                                                                 |
| `agent`                     | 是   | 当前 agent id 与展示名。                                                               |
| `run`                       | 是   | 当前 run id。                                                                          |
| `iteration`                 | 是   | 本节点在本 run 的第几次激活 / 上限；没有上限时写 `n / ∞`。                          |
| `receiver`                  | 是   | 命中的接收器 id 与展示名。                                                             |
| `rule`                      | 是   | 该接收器的 channel id 数组，例如 `[review]` 或 `[spec, tests]`。                   |
| `queue`                     | 否   | 本 activation 入队时，前面还有多少个待执行 activation；用于让 agent 知道大概等待情况。 |
| `goal`                      | 否   | run 启动时用户 brief 的纯文本；没有则为空。                                            |

### 4.2 inputs

`inputs` 必须列出命中的 `receiver.rule` 里的**全部 channel**，每个 channel 恰好一条交付物。不会出现“只给一半输入”的 activation。

每个输入至少包含：

| 字段             | 含义                                                                 |
| ---------------- | -------------------------------------------------------------------- |
| `channel`      | 输入 channel id 与展示名。                                           |
| `artifact`     | artifact id。                                                        |
| `kind`         | `text` 或 `json`。                                               |
| `producer`     | 生产者的 pipeline/node/agent；external/user 写 `external/user`。   |
| `producedBy`   | 产生该 artifact 的 activation id；external 可省略。                  |
| `summary`      | 生产者提交时给的摘要；用于不内联时快速判断。                         |
| `schema`       | json artifact 的 schema 路径；text 省略。                            |
| `schemaSha256` | schema 文件哈希；用于判断契约是否变化。                              |
| `path`         | canonical 内容文件路径；agent 需要全文时读取。                       |
| `sha256`       | 内容哈希；用于防止读到被替换的文件。                                 |
| `content`      | 内联内容；是否出现由 channel 的 `delivery.inline` 与大小上限决定。 |

输入消费规则：

- 每个 channel 取 FIFO 队首一份；该 channel 的其余积压留到后续 activation。
- 一旦 dispatch，输入原子标记为已消费；本次 activation 内重复读同一 path 不会重复计数。
- artifact 内容不可变；agent 不应修改 artifact 文件，只读。

### 4.3 输出选择（不在 activation 里）

输出通道是 pipeline 的静态配置，不是本次 activation 的派发内容。引擎在 provision 时，把该 agent 在所有 placement 下可用的出通道写入**系统提示词**的「可用输出通道」段，按 `pipeline/node` 分组，列出：

- channel id、展示名；
- `kind`（text/json）与 json 的 schema；
- `required`；
- 固定目标：`pipeline/node/receiver` 或 `external/file <path>`。

activation 消息**不重复这份清单**，也不预先规定“这次必须输出给谁”。agent 在任务执行中根据实际情况选择通道；channel 的 `to` 是固定目标，所以选择 channel 就等于选择接收器或 file sink。

这样做的原因：

- 同一 agent 在不同 run、不同输入下可能走不同分支，提前在 activation 里锁定输出会逼它走错路径；
- 输出通道在会话生命周期内基本稳定，放进系统提示词可以保持前缀缓存；
- activation 只承载“本次输入 + 本次任务”，语义更单一。

agent 调用 `team_submit_artifact` 时：

- 目标是 receiver：给 `channelId` + `receiverId`；引擎校验 `receiverId` 与 `channel.to.receiverId` 一致；
- 目标是 external/file：只给 `channelId`，引擎按配置落盘；
- 只能提交当前 node 的出通道，不能替其他 agent 提交；
- `required=true` 的通道必须在 `team_finish` 前成功提交过；`required=false` 的可按情况跳过；
- 如果配置里有多条互斥的可选路径，不要把每一条都标成 `required`，否则 agent 无法只选其中一条。

### 4.4 instructions

`instructions` 是 `node.instructions` 的模板渲染结果。支持：

- `{{team.*}}`、`{{agent.*}}`、`{{pipeline.*}}`、`{{node.*}}`
- `{{run.id}}`、`{{activation.id}}`、`{{activation.iteration}}`
- `{{receiver.id}}`、`{{receiver.rule}}`
- `{{goal}}`

node instructions 只放本次任务要求，不放工具说明、团队协议、其他节点的职责。

### 4.5 completion

末尾固定重复四条最容易出错的规则：

1. 输出通道在系统提示词里；按当前 node 与实际情况选择 `channel`，不要等 activation 给出输出清单。
2. 通过 `team_submit_artifact` 提交；receiver 目标必须给 `receiverId` + `channelId`。
3. 全部 required 输出被接受后调用 `team_finish`。
4. 不修改 `.dsh/.dsh-workspace-team/`。

这些规则在系统提示词里也有完整版；activation 里只做短提醒，避免 agent 在长上下文中漏掉。

## 5. 完整示例

builder 的 `rework-inbox` 接收器满足，收到 review：

```text
[team:activation] act_01J9Z6QK3M
protocol: 1
team: product-delivery (产品交付团队)
pipeline: delivery (需求交付)
node: builder (实现)
agent: builder (实现者)
run: run_01J9Z5A1
iteration: 2 / 4
receiver: rework-inbox (返工接收器)
rule: [review]
queue: 前面还有 0 个待执行 activation
goal: 为 CLI 增加 --json 输出

inputs:
- channel: review (评审意见)
  artifact: art_01J9Z6P0
  kind: json
  producer: delivery/reviewer (评审者)
  producedBy: act_01J9Z5R7
  summary: 需要处理 2 个 blocker
  schema: schemas/review.schema.json
  schemaSha256: 7f3c...
  path: .dsh/.dsh-workspace-team/runs/run_01J9Z5A1/artifacts/art_01J9Z6P0/content.json
  sha256: 91ab...
  content: {
    "status": "changes_requested",
    "comments": [
      { "file": "src/cli.ts", "issue": "--json 时仍输出人类可读摘要" },
      { "file": "test/cli.test.ts", "issue": "缺少 --json 的断言" }
    ]
  }

instructions:
处理 review 里的两条 blocker；补测试；提交实现报告。
不要修改评审者的结论，也不要直接和 reviewer 对话。

completion:
- 按系统提示词中的可用输出通道，结合当前 node 与实际情况选择 channel
- 目标是 receiver 时同时给 receiverId 与 channelId
- 全部 required 输出被接受后调用 team_finish
- 不要修改 .dsh/.dsh-workspace-team/ 下的配置与状态文件
```

本例中 builder 的 `build-report` 出通道写在系统提示词里，activation 只给 review 输入和任务说明。

## 6. 和系统提示词、用户消息的区别

|              | 系统提示词               | bootstrap 消息   | activation 消息        | 用户聊天（主 Agent；worker UI 默认 blocked） |
| ------------ | ------------------------ | ---------------- | ---------------------- | ---------------------- |
| 发送时机     | 会话初始化               | 初始化后一次     | 接收器满足并 dispatch  | 用户随时               |
| 角色         | system                   | user             | user                   | user                   |
| 内容         | 角色 + 团队协议 + 输出通道 + roster | 身份/接收器/待命 | 本次任务 + 输入 | 人类的话               |
| 是否重复     | 固定前缀                 | 只一次           | 每 activation 一次     | 每次用户输入           |
| 是否授权工作 | 否                       | 否               | **是**           | 否                     |

用户聊天可以进入任一会话，包括 worker；但 Web UI 默认 block worker 的 composer，此时用户只能通过主 Agent 会话输入，API/其他客户端仍可直接输入。activation FIFO 只排序 activation；用户直接消息由 DSH 会话按普通输入处理，不进入该 FIFO，也不改变 activation 状态。若 activation 正在等待回答，引擎观察到 user-role 消息会按 [人工交互契约](./人工交互契约.md) 标记 answered；否则只记 `human.direct-input`。Suggestion 仍可由主 Agent 转达，在 `queue` 模式下作为 `[team:suggestion]` 段追加在 activation 消息里；answer 以 `[team:answer]` 投递。直接聊天、suggestion、answer 可以同时存在，不保证顺序，agent 需按消息类型区分。

## 7. 失败、重试与幂等

- **发送失败**：消息未确认进入会话时，activation 回到 dispatching，输入不消费；重试同一 activation id。
- **agent 未 finish**：回合结束但没 `team_finish`，引擎先提醒；超过 `idleGraceMs` 判失败，按 `activation.onFailure` 处理。
- **重试**：复用同一组输入和同一 activation id，不重新消费 channel 队首；消息里带同一个 `act_...`，避免 agent 以为是新任务。
- **重复投递**：agent 可能收到重复的 `act_...`；按 activation id 幂等，不重复提交输出。
- **取消**：取消后不再发送；已消费输入是否释放由取消阶段决定，事件日志记录。

## 8. 版本化

- `protocol: 1` 是消息信封版本；新增可选字段不升版本，删除/改义才升。
- 旧 agent 会话不保证能理解新协议；升级引擎时，新 activation 使用新模板，必要的话重建会话。
- 事件日志保存完整消息或其规范化副本，便于回放和排障。
